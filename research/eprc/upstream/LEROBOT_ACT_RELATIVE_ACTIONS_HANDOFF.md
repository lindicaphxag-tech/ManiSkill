# LeRobot ACT relative-actions upstream handoff

Target issue: https://github.com/huggingface/lerobot/issues/3312

Maintainer guidance in the issue says relative actions are currently implemented
for Pi0/Pi0.5 and explicitly welcomes an ACT integration PR.

## Audited upstream

- repository: `huggingface/lerobot`
- commit: `ca69a2068462a37f7cdcb74180927a2f863d2bf7`
- ACT config: `src/lerobot/policies/act/configuration_act.py`
- ACT processor: `src/lerobot/policies/act/processor_act.py`
- shared relative processor:
  `src/lerobot/processor/relative_action_processor.py`

## Minimal design

The patch does **not** add new relative-action math.

It reuses the existing LeRobot contract:

```text
raw absolute action
  -> relative to observation.state
  -> normalize
  -> ACT
  -> unnormalize
  -> absolute using the cached generation-time state
```

The default ACT pipeline is left unchanged when
`use_relative_actions == False`.

When enabled, ACT gets the same three configuration fields already used by Pi0
and related policies:

- `use_relative_actions`
- `relative_exclude_joints`
- `action_feature_names`

`action_feature_names` is already populated by the generic `make_policy`
path from dataset metadata.

## Chunk-anchor correctness

No ACT-specific queue code is added.

The shared `RelativeActionsProcessorStep` already keeps the cached anchor while
a policy chunk is in flight. Production `lerobot_eval.py` and rollout context
already call `bind_relative_anchor(policy, preprocessor)`, so an ACT policy
using this pipeline inherits the same chunk-held anchor semantics.

This directly avoids the failure mode discussed in #3312: re-anchoring later
actions in one predicted chunk against newer observations.

## Scope

Exactly three upstream files:

1. ACT config: add standard relative-action fields;
2. ACT processor: insert existing paired relative/absolute steps only when
   enabled;
3. ACT processor tests: verify order, excluded gripper semantics, and exact
   relative→absolute round trip.

No changes to:

- policy model weights or forward pass;
- shared relative-action implementation;
- rollout engine;
- queue implementation;
- default ACT behavior.

## External-adoption boundary

This is a PR-ready handoff only. It is not LeRobot adoption until an upstream PR
is submitted and retained by maintainers.


## Patch generation

The checked-in handoff is an exact-source transformer rather than a hand-written
unified diff. Validation runs it against the pinned LeRobot commit, requires
exactly the three expected changed files, executes `git diff --check`, runs the
official ACT processor test file, and uploads the resulting `git diff --binary`
as a workflow artifact. The artifact is therefore generated by Git from the
validated checkout rather than manually maintained.
